# Модуль 1: Штатные маленькие тесты (Nominal Small Tests)

Полная спецификация маленьких штатных тестов для верификации отдельных REST эндпоинтов и Protobuf-сообщений бэкенда SyncMate.

---

## 1. HTTP REST API Тесты

### REST-1: Регистрация пользователей и многопоточность (`POST /api/v1/auth/register`)
- **Входное состояние**: Очищенная БД.
- **Действия**: Циклическая регистрация 10 пользователей + 5 одновременных параллельных запросов (`asyncio.gather`).
- **Ожидаемое состояние**: Все 15 пользователей созданы, ID уникальны, JWT токены высланы.

### REST-2: Авторизация и инвалидация токенов (`POST /api/v1/auth/login`)
- **Входное состояние**: Зарегистрированный пользователь с токеном `Token_V1`.
- **Действия**: Повторный вход пользователя.
- **Ожидаемое состояние**: Выдается `Token_V2`, запрос со старым `Token_V1` возвращает `401 Unauthorized`.

### REST-3: Запрос полного и неполного профиля (`GET /api/v1/profile`)
- **Входное состояние**: Участник А (профиль заполнен), Участник Б (вес/рост `null`).
- **Действия**: Вызов `GET /profile` для обоих пользователей.
- **Ожидаемое состояние**: HTTP `200 OK` для обоих; у Б поля `weight_kg` и `height_cm` равны `null`.

### REST-4: Серия обновлений профиля (`PUT /api/v1/profile`)
- **Входное состояние**: Начальный вес 70.0 кг.
- **Действия**: 3 последовательных апдейта веса (`72.0` -> `75.0` -> `73.5` кг).
- **Ожидаемое состояние**: Данные обновлены, повторный запрос возвращает `73.5` кг.

### REST-5: Создание комнат за временное окно (5–15 сек) (`POST /api/v1/rooms`)
- **Входное состояние**: Система комнат.
- **Действия**: В течение 5–15 секунд генерируем максимальный поток комнат.
- **Ожидаемое состояние**: 100% сгенерированных `invite_code` уникальны, дубликаты отсутствуют.

### REST-6: Тяжелая инициализация по коду с оффлайн-профилем (`GET /api/v1/rooms/join/:code`)
- **Входное состояние**: Комната с бегунами. Пользователь Б имеет незаполненный профиль.
- **Действия**: Пользователь Б вызывает инициализацию по коду комнаты.
- **Ожидаемое состояние**: HTTP `200 OK`, пользователя пускает в комнату, возвращается полное состояние и накопленные треки напарников.

### REST-7: Запрос погоды и проверка кэша (`GET /api/v1/weather`)
- **Входное состояние**: Координаты `55.7558, 37.6173`.
- **Действия**: 5 запросов погоды подряд.
- **Ожидаемое состояние**: HTTP `200 OK`, отдача из кэша сервера.

## 2. WebSocket & Protobuf Тесты

### WS-1: Сокет Handshake
- **Входное состояние**: Валидный токен.
- **Действия**: Подключение к `wss://server/ws`.
- **Ожидаемое состояние**: Статус `101`, выдан `slot_id`.

### WS-2: Одиночная точка телеметрии (`UserPointMessage`)
- **Входное состояние**: Активный сокет.
- **Действия**: Отправка 1 точки.
- **Ожидаемое состояние**: Рассылка `RoomStateBroadcast` всем напарникам.

### WS-3: Градация батчей (2, 20, 200 точек) и параллельные батчи
- **Входное состояние**: Бегуны А и Б переподключились.
- **Действия**: А отправляет 20 точек, Б одновременно отправляет 200 точек.
- **Ожидаемое состояние**: Атомарное сохранение обоих батчей, рассылка обновленных линий маршрутов без потерь.

### WS-4: Смена состояний `STATE_READY` / `STATE_PAUSED`
- **Входное состояние**: Пользователь в сокете.
- **Действия**: Переключение статусов.
- **Ожидаемое состояние**: Обновление состояний в рассылке сокета.

### WS-5: Выход из комнаты (`STATE_LEFT`)
- **Входное состояние**: Активный участник.
- **Действия**: Отправка `STATE_LEFT` и закрытие сокета.
- **Ожидаемое состояние**: Сброс данных активного участия, у напарников отображается `STATE_LEFT`.

### WS-6: Запуск отсчета 3..2..1 (`ACTION_SET_START_COUNTDOWN`)
- **Входное состояние**: Админ в лобби.
- **Действия**: Запуск таймера 5 секунд.
- **Ожидаемое состояние**: Рассылка отсчета всем участникам.

### WS-7: Глобальный старт и блокировка неполных профилей (`ACTION_BEGIN`)
- **Входное состояние**: А (профиль заполнен), Б (вес `null`).
- **Действия**: Б пытается встать в `STATE_READY`, Админ шлет `ACTION_BEGIN`.
- **Ожидаемое состояние**: Пользователю Б отказано в старте, А автоматические переведен в `STATE_ACTIVE`.

### WS-8: Изменение цели на ходу (`ACTION_SET_GOAL`)
- **Входное состояние**: А бежит, Б на паузе.
- **Действия**: Админ меняет цель на 10 км.
- **Ожидаемое состояние**: Новая цель приходит и А, и Б на паузе.

### WS-9A: Бан участников (`ACTION_BAN`)
- **Входное состояние**: А бежит, Б на паузе, В вышел (`STATE_LEFT`).
- **Действия**: Админ банит А, Б и В.
- **Ожидаемое состояние**: Все трое помещаются в Blacklist комнаты, сокеты разрываются.

### WS-9B: Разбан и старт с 0 (`ACTION_UNBAN`)
- **Входное состояние**: Участник В в Blacklist.
- **Действия**: Админ разбанивает В, В перезаходит по ссылке.
- **Ожидаемое состояние**: В заходит как новый бегун с чистого листа (с 0 дистанции).

### WS-10: Финиш и полная тишина для выбывших (`ACTION_TERMINATE`)
- **Входное состояние**: А бежал до 10:30, Б на паузе с 10:15, В вышел, Г забанен.
- **Действия**: Админ отправляет `ACTION_TERMINATE`.
- **Ожидаемое состояние**: Время Б фиксируется на 10:15, вышедшим В и Г в сокет ничего не прилетает (полная тишина).
